## 一、项目目标与需求概述

本项目实现一个基于 MongoDB 的在线问卷系统。注册用户可以创建、编辑、发布和关闭问卷，通过访问链接邀请其他已登录用户填写，并查看系统根据回答数据实时生成的统计结果。

系统主要实现以下功能：

1. 用户注册、登录、退出和会话管理。
2. 创建问卷，设置标题、说明、截止时间、匿名填写和重复填写规则。
3. 支持单选、多选、文本填空和数字填空四种题型。
4. 为题目设置必答、数量、长度和数值范围等校验规则。
5. 根据用户答案动态跳转到后续题目。
6. 通过公开链接供多人填写问卷，但填写者必须先登录。
7. 支持匿名保存回答和限制同一用户重复填写。
8. 自动生成整个问卷或单道题目的统计结果。
9. 使用 MongoDB 保存业务数据并通过聚合管道完成统计。

其中，“允许匿名填写”表示回答记录中不保存可展示的填写者身份，并不表示可以免登录填写。系统仍要求填写者登录，以便进行权限判断和重复提交控制。

## 三、主要功能实现

### 3.1 用户账号与权限

- 新用户可以使用唯一用户名和不少于 8 位的密码注册。
- 密码使用 scrypt 加盐哈希保存，不保存明文。
- 登录状态通过签名 Session Cookie 维护。
- 创建、编辑、发布、关闭和查看统计都需要登录。
- 所有问卷管理接口都会同时检查当前用户和问卷的 `owner_id`，避免通过修改 URL 操作他人的问卷。
- 填写者打开问卷链接时也必须先登录；未登录访问会跳转到登录页，登录后返回原问卷。

### 3.2 问卷创建与管理

创建者可以：

- 新建问卷并填写标题和说明。
- 设置截止时间。
- 设置是否允许匿名保存回答。
- 设置是否允许同一用户重复填写。
- 查看自己创建的问卷列表。
- 发布问卷并获得 `/survey/{public_id}` 访问链接。
- 关闭问卷，停止接收新的回答。

问卷状态包括：

- `draft`：草稿，可以继续编辑，不能填写。
- `published`：已发布，可以通过公开链接填写。
- `closed`：已关闭，不再接受回答。

### 3.3 题型与校验规则

系统支持四种题型：

| 题型 | 可配置内容 | 服务端校验 |
|---|---|---|
| 单选题 | 选项、是否必答 | 答案必须属于给定选项 |
| 多选题 | 选项、最少和最多选择数、是否必答 | 每项必须合法，并检查选择数量 |
| 文本填空 | 最短和最长字符数、是否必答 | 检查文本长度 |
| 数字填空 | 最小值、最大值、是否只允许整数、是否必答 | 检查数字格式、范围和整数要求 |

浏览器端校验用于改善填写体验，服务端会再次执行相同规则，防止绕过网页直接提交非法数据。

### 3.4 条件跳转

题目可以根据当前答案跳转到某一道后续题目。支持以下条件：

- 单选答案等于某个值。
- 多选答案包含某个值。
- 数字答案大于、大于等于、小于或小于等于某个值。

规则匹配时，系统按题目 `order` 从第一题开始，依次检查当前题目的跳转条件；匹配则进入目标题，没有匹配则进入下一题。浏览器即时更新页面，提交时服务器重新计算真实答题路径，只校验和保存实际访问过的题目，并检查无效目标题。

编辑器只允许跳转到后续题目，服务器还会记录已访问题目并检测循环，从而避免错误规则导致无限跳转。

### 3.5 填写、匿名与重复提交

- 填写者必须登录后才能打开问卷。
- 多名已登录用户可以同时填写同一份问卷。
- 允许匿名时，回答文档的 `respondent_id` 保存为 `null`，创建者无法从统计中看到填写者身份。
- 不允许重复填写时，系统基于问卷 ID、登录用户 ID 和服务器密钥生成不可逆 HMAC 去重键。
- 该去重键只用于判断同一账号是否已提交，不在统计页面展示。
- 允许重复填写时，同一账号可以多次提交。

### 3.6 统计结果

统计结果从 `responses` 集合中的实时数据自动生成：

- 单选题：显示每个选项的次数，包括 0 次选项，并显示该题回答人数。
- 多选题：统计每个选项被选择的次数，包括 0 次选项。
- 文本题：展示所有填写内容。
- 数字题：显示回答数、平均值、最小值、最大值和全部数值。
- 创建者可以查看整个问卷的统计，也可以只查看某一道题的统计。

## 四、MongoDB 数据库设计

### 4.1 集合划分

系统使用三个主要集合：`users`、`surveys` 和 `responses`。

#### users 集合

```javascript
{
  _id: ObjectId,
  username: String,
  password_hash: String,
  created_at: Date
}
```

`username` 建立唯一索引，密码只保存哈希、盐和参数。

#### surveys 集合

```javascript
{
  _id: ObjectId,
  owner_id: ObjectId,
  public_id: String,
  title: String,
  description: String,
  allow_anonymous: Boolean,
  allow_multiple: Boolean,
  status: "draft" | "published" | "closed",
  deadline: Date | null,
  questions: [Question],
  created_at: Date,
  updated_at: Date,
  published_at: Date | null,
  closed_at: Date | null
}
```

题目作为子文档嵌入 `questions` 数组：

```javascript
{
  _id: String,
  prompt: String,
  type: "single" | "multiple" | "text" | "number",
  required: Boolean,
  options: [String],
  validation: {
    min_choices: Number,
    max_choices: Number,
    min_length: Number,
    max_length: Number,
    min_value: Number,
    max_value: Number,
    integer_only: Boolean
  },
  jump_rules: [{
    _id: String,
    operator: "equals" | "contains" | "gt" | "gte" | "lt" | "lte",
    value: String,
    target_question_id: String
  }],
  order: Number
}
```

题目与问卷通常一起读取，而且题目只属于一个问卷，不需要跨问卷共享，因此采用嵌入设计。这样能一次读取完整问卷，并保持题目顺序和设置的一致性。

阅读这一设计后，我理解了嵌入与独立集合的取舍：题目数量相对有限、总是随问卷读取，适合嵌入；回答数量持续增长，则应单独保存。若后续需要超大型问卷或可复用题库，可以将题目迁移到独立集合，而不必重新设计用户和回答集合。

#### responses 集合

```javascript
{
  _id: ObjectId,
  survey_id: ObjectId,
  respondent_id: ObjectId | null,
  is_anonymous: Boolean,
  single_submission_key: String,
  answers: [{
    question_id: String,
    value: String | Number | [String]
  }],
  visited_question_ids: [String],
  submitted_at: Date
}
```

回答使用独立集合，原因如下：

- 问卷回答数量可能持续增加，不适合无限嵌入问卷文档。
- 多人同时提交时不会竞争修改同一份问卷文档。
- 便于按问卷查询、分页和执行聚合统计。
- 统一的 `{question_id, value}` 结构可以保存不同题型的答案。

匿名回答的 `respondent_id` 为 `null`；若禁止重复填写，则通过 `single_submission_key` 进行控制。

### 4.2 索引设计

| 索引 | 类型与用途 |
|---|---|
| `users.username` | 唯一索引，防止用户名重复 |
| `surveys.public_id` | 唯一索引，保证访问链接唯一 |
| `surveys.owner_id + created_at` | 复合索引，加快个人问卷列表查询 |
| `surveys.status + deadline` | 复合索引，辅助状态与截止时间查询 |
| `responses.survey_id + submitted_at` | 复合索引，加快回答和统计查询 |
| `responses.survey_id + single_submission_key` | 条件唯一索引，禁止同一用户重复提交 |

### 4.3 聚合统计设计

系统通过 MongoDB 聚合管道完成统计：

- `$match` 选择指定问卷的回答。
- `$unwind` 拆分 `answers`；多选题再次拆分选项数组。
- `$group` 统计选项次数，或计算数字平均值、最小值和最大值。
- `$sort` 按次数或结果顺序整理数据。

与把所有回答读入 Python 后再处理相比，这种方式更能利用 MongoDB 的聚合能力，并减少应用层的数据处理量。

## 七、用户操作流程

### 7.1 创建者流程

1. 注册并登录账号。
2. 点击“新建问卷”。
3. 填写标题、说明、截止时间、匿名和重复填写设置。
4. 添加单选、多选、文本或数字题目。
5. 根据题型设置选项和校验规则。
6. 如需跳题，在已有题目下设置条件、比较值和后续目标题。
7. 点击“发布问卷”。
8. 复制访问链接并发送给填写者。
9. 在“我的问卷”中点击“统计”查看实时结果。
10. 不再接收回答时点击“关闭”。

### 7.2 填写者流程

1. 注册或登录账号。
2. 打开创建者提供的问卷链接。
3. 按页面提示逐题回答。
4. 系统实时检查必答、选择数量、文本长度和数字范围。
5. 满足跳转条件时自动进入目标题。
6. 完成最后一道实际访问的题目后提交问卷。

## 九、问题与解决方法

### 9.1 登录要求与匿名填写的关系

我重新阅读作业文档，注意到“填写问卷的人需要先登录”，随后把这一段和匿名填写、统计要求的截图发给 AI，要求重新核对。这是我主动提出的一次需求纠偏：原先将匿名填写理解为免登录，与原文存在冲突。

AI 据此调整了填写入口和提交处理。最终实现中，登录用于确认账号与控制重复填写，匿名则表示回答记录不保存 `respondent_id`；HMAC 键用于去重，统计页面不展示该键。由此我理解到，账号认证、回答身份展示和重复提交控制是三个需要分别处理的问题。

### 9.2 Python 3.9 兼容问题

我先在终端运行 `python --version`，得到 Python 3.9.12；安装完成后执行 `python run.py`，又把启动失败的完整截图反馈给 AI。错误中出现 `unsupported operand type(s) for |`，说明依赖安装成功后仍可能存在代码与解释器版本不兼容的问题。

AI 将不兼容的 `X | None` 写法改为 `typing.Optional`，并在 Python 3.9.12 下运行自动测试。随后我重新启动并打开登录页，确认应用可以进入实际操作流程。代码修改由 AI 完成，我的参与是确认环境、复现错误、提供证据和继续验证。

### 9.3 依赖下载失败

我先执行依赖安装，遇到 SSL 下载错误；按 AI 建议更换镜像后，错误进一步显示为 `ProxyError`。我没有仅根据最后一行“找不到 fastapi 版本”判断包不存在，而是继续按排查步骤提供实际结果。

我依次执行了 `set | findstr /i proxy`、`python -m pip config list -v`，以及查询 `urllib.request.getproxies()` 的命令。环境变量查询没有显示代理，但 Python 读取到 `127.0.0.1:7897` 的代理配置。AI 根据这些输出定位到本机代理问题，指导调整连接方式；随后安装出现 `Successfully installed`，我再继续启动应用。

这次排查使我理解到：软件包安装失败可能是网络连接未建立，系统代理也不一定出现在终端环境变量中。先收集错误发生在哪一层，比直接更换依赖版本更有依据。

### 9.4 跳转规则可能形成循环

AI 在实现中限制目标题只能是后续题目，并在服务器端检测重复访问。我在编辑器中配置跳转和试填时，重点观察“跳到了哪一题”和“被跳过的题目是否出现在统计中”。

结合实现，我的理解是：界面上的跳题只说明交互发生了变化，服务端仍应重新核对访问路径。两边都检查，才能避免只修改浏览器提交内容就绕过规则。

### 9.5 Jinja 字典键与方法重名

AI 在端到端检查中发现，统计数据使用的 `items` 和 `values` 与 Python 字典方法重名，导致 Jinja 点号访问出错。AI 将模板改用方括号访问，修复统计页面渲染。

这项修复来自 AI 的代码和测试检查；我在浏览器中提供了实际统计页面，用于确认文本和数值可以显示。整理这一问题后，我理解到数据库已经保存数据与页面能够正确显示数据，需要分开验证。

### 9.6 不同题型答案结构不同

系统把回答统一保存为 `{question_id, value}` 数组，`value` 可以是字符串、数字或字符串数组。这样既保留统一的查询结构，也利用了 MongoDB 文档字段类型灵活的特点。

### 9.7 依赖与运行环境补充

开发期间，AI 还补充了会话签名所需的 `itsdangerous` 依赖，并调整了 Windows 环境下的时区处理，减少额外时区数据库带来的启动障碍。这些修改属于 AI 协助完成的环境适配，保留在这里是为了说明实际运行需要同时检查代码、依赖和本机环境。

### 9.8 跳转目标的显示方式

早期编辑页用内部题目 ID 显示跳转目标，不便于核对。我提供的页面截图保留了这一情况；后续 AI 将显示内容调整为题目文字。我的验收关注点因此不只包括按钮是否可以点击，也包括配置结果是否容易看懂、能否与实际题目对应。

## 十一、安全性与当前限制

### 11.1 安全注意事项

- 不要把 `.env` 提交到公开仓库。
- 正式部署必须更换 `SESSION_SECRET`。
- 正式环境应启用 HTTPS，并将 SessionMiddleware 的 `https_only` 设置为 `True`。
- 生产系统还应增加 CSRF 防护、请求限流、审计日志和更严格的输入过滤。

### 11.2 当前限制

- 编辑器只支持跳转到后续题目。
- 页面以课程演示为目标，没有实现复杂的拖拽排序。
- 当前未实现问卷版本管理和导出统计文件。
- 当前部署方式适合本地演示，不等同于生产环境配置。

题型、校验规则和跳转规则都以数据形式保存在 MongoDB 中，核心逻辑与路由分离，因此第二阶段可以继续增加题型、问卷版本、导出功能或更复杂的统计，而不需要重新设计整个系统。
